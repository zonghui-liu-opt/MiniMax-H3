# 猫咪动作内网测试：问题定位与 v3 改写

日期：2026-09-08。

结论：现有问题同时涉及动作目标写偏、过度限制自然反应、复杂动作被压进闭环，以及可能的请求条件／时长不一致。官方提示词结构值得继续采用，但不能代替正确的动作设计。

证据范围：已读取 `metadata_smoke_v1.csv`、`metadata_smoke_v2.csv`、v2 模板／提示词包、当前批处理代码、官方 prompt skill 及基础模式指南；已对用户提供的两段本地视频逐段抽帧，并查看三张 smoke 猫图。没有查看本轮内网失败视频、实际请求 JSON 或服务端日志。因此下文区分可从文本／画面／代码确认的事实和仍待内网验证的解释。

## 1. 不使用官方 skill 时出现额外物体

用户观察表明，按官方 skill 改写的结果在控制画面内容方面更好；后续继续以它为固定流程。官方指南要求先明确输入模式，再描述构图、主体、环境、可见动作和声音，最后用规定字段组织内容。这有助于把“谁出现、在哪里、做什么”写清楚。

不能据此认定“只要用三个字段就不会生成额外物体”。skill 是编写指引，不是模型侧的硬约束或物体过滤器。物体边界、动作暗含的参与者、模型采样和实际参考条件仍可能影响结果。比如“被拽”“被挠”通常暗含施动者；食盘无来源地出现也需要生成一个入场过程。

另一个需要核对的事实：本地 v1 和 v2 CSV 都已经使用了官方的首尾图对齐行及三个字段。它们不能直接当作“无官方格式”和“有官方格式”的纯对照。若用户的无 skill 组是更早的原始 prompt，应以实际送到服务端的那份文本为准。

改写：以正面的画面内容定义为主——猫、参考背景，或猫与唯一指定道具；对人手只做必要的一句排除，不长篇罗列无关物体。锁定猫的外观和场景，让眼睑、头部、呼吸与重心随动作自然变化。

## 2. 呼吸＋眨眼：漏眨眼、表情呆板

可确认的旧文本：呼吸被写成 `barely perceptible`、`minute local change`；眨眼只在 0.95–1.20 秒出现一次。它还要求头部朝向、耳朵、爪子、后躯和尾部稳定，3.20 秒呼吸已在视觉上停止，3.60 秒后保持终点姿势。

较可能的机制：在全身景别中，唯一一次短眨眼只是很小的局部事件；提示词的大量篇幅却强调稳定和完全复位。小动作容易在生成中变弱或缺失。呆板感则与明确写出的静止要求一致：文字主动删除了微小头部反应、目光调整和持续呼吸。

“保持同一只猫”应约束面部比例、眼睛颜色和花纹，不应等价于眼睑开合、视线和头部角度始终不变。“自然表情”也应落到可见细节，不能只加一个形容词。

v3：把完整慢眨眼放在动作描述开头；约 1.00–1.80 秒完成闭眼、短暂完全闭合、再睁开，扩大可见性；配合轻微低头、目光调整、肩胸呼吸。保留坐姿闭环，但只在结尾到达参考状态，取消长时间冻结。该时间安排是测试设计，不是模型保证。

验收：两眼都出现完整闭合和重新张开；至少能看到轻微呼吸或头部反应；没有把“自然表情”生成成人类式夸张笑容。

## 3. 左／右耳：像按压，恢复生硬，缺乏反应

可确认的旧文本：动作核心是 `local flex`，外力只被泛称为轻力；向画面侧边的运动只是一个很弱的分量。0.90–1.70 秒维持峰值阶段，1.70 秒才释放；还要求另一耳、眼睛、头和身体稳定。

较可能的机制：局部弯折本身既可表现为向外牵引，也可表现为向下压折。旧文没有明确“耳尖领先、远离头顶、略向上”的轨迹；持续峰值也弱化了“短促拽一下”的观感。头部完全不跟随、眼睛毫无反应又让局部形变像独立橡胶动画。

v3：明确猫自身左右与画面左右；耳尖向外略向上移动，耳根保持连接，耳廓长度和特征形态保持一致；随后迅速释放，先回弹，再有一次幅度更小的收稳。允许头部微微跟随、眼睑短暂收窄并重新打开，身体保持平衡和呼吸。

限制：没有可见接触点时，“被轻拽”的因果感仍然较难稳定，只能先通过位移方向、释放节奏和身体反应强化视觉表达。折耳、卷耳与大直耳应分别复测，不能把所有猫都改成标准直耳或同样的拉伸形变。

验收：耳尖主要向外离开头顶，不向下贴压；耳根不漂移、不拉长；回弹逐渐收稳；眼睛和头部有轻微伴随反应。

## 4. 左／右打滚：旧文没有要求露腹和空中挥爪

素材 7 时长约 8 秒。约 4–5.5 秒可看到坐姿经过侧倾、仰躺转为腹部朝上；后半段前爪弯起并在空中活动，同时出现人手抚摸。需要迁移的是猫的姿态链和放松反应，人手不属于目标内容。

可确认的旧文本：明确写 `partial roll onto the ... flank`，随后让同侧前爪朝画面侧面伸出。它没有要求背部着地、腹部朝上，也没有让双前爪离地、在胸腹上方挥动。恢复坐姿从 2.10 秒就开始。

因此，这是动作定义与目标不一致：旧文即使被完全执行，也不会得到素材 7 后面的露肚皮打滚。

v3：坐姿放松 → 向指定侧倾倒 → 肩与髋继续翻转直到背部着地 → 腹部朝上且可见 → 双前爪悬起，其中一爪轻挥一次 → 保持放松露腹。暂按 6 秒、仅首帧条件设计，取消强制回坐；以眼睑变柔、头贴地、肩髋小幅摇动表达自然状态。

画面空间：三张 smoke 图都是较窄的竖幅正坐全身图。横向摊开会改变占画宽度。v3 用紧凑的对角线姿态保留空间；如果仍裁切，应另测更宽构图的首图，而不是让猫缩放或变形来硬塞进原图。不得把参考视频的镜头远近变化误当作目标必需内容。

验收：腹部可见，背部／后侧着地，双前爪离地并有一次明确空中小挥动；没有人手；没有仅向前探爪。

## 5. 吃猫粮：动作链太长，进食时间被道具进出和复位占用

可确认的旧时间表：0.40–0.90 秒食盘入场；0.90–1.35 秒低头；1.50 和 1.90 秒各吃一口；2.10–2.35 秒鼻推食盘；2.35–2.80 秒抬头；3.30 秒食盘完全退场；3.50 秒已恢复参考状态。

这给两口食物、咀嚼和停顿留下的时间非常少。“从容”一词无法消除如此紧凑的事件安排。强制空场尾图又要求食盘必须消失，额外制造了不必要的退场动作。

v3：暂按 8 秒、仅首帧条件设计。食盘缓缓进入并停住 → 猫低头短暂嗅闻 → 吃一小口并有咀嚼停顿 → 再吃一口。结尾仍在从容进食，食盘留在地面。依据用户提出的可不复位方向，主动删除“鼻推盘”和“盘退出画面”；如果业务仍需要推盘，可另设后续独立动作，避免再塞进本段。

仍待测的道具环节：猫首图没有食盘，所以 v3 保留了原设计中的滑入方式。若滑入不自然，下一次可另做含静止食盘的首图以取消入场阶段，但这会改变首帧，应作为独立变量测试。

验收：可见嗅闻／进食间隔和小幅咀嚼；盘不漂移、不消失；结尾无需突然抬头回坐。

## 6. 入睡：参考其实是蜷卧收身，不是展开侧躺再坐起

《过渡动画》时长约 15 秒。开头有较长待机，随后低头、收前腿、降低胸腹、收拢后躯，约后半段形成紧凑蜷卧，最后头枕前爪、闭眼保持。它没有立刻重新坐起。需要压缩的是前面的等待和过长铺垫，并保留完整的收身动作。

可确认的旧文本：先让左／右肩触地、形成侧躺姿态，2.25 秒就准备睁眼，2.45 秒开始起身，3.55 秒必须恢复正坐。这与参考的终态不同，也没有明确“前爪留在胸下、胸腹下降、身体收成椭圆、头枕前爪”的结构。

较可能的失败机制：同图尾帧把终点强行拉回坐姿，大幅下卧动作又描述得不够清楚，模型可能退化为较小的前倾／探爪。这里的“退化”是根据用户结果和文本冲突的推断，需要失败视频和去尾帧对照验证。

v3：命名改为“向左／右收身蜷卧入睡”。仅首帧、暂按 6 秒；约 1.00–3.50 秒完成转肩、收腿、胸腹下沉与后躯合拢；3.50–4.50 秒头枕前爪并闭眼；末段保持睡姿与轻微呼吸。方向以初始正坐时猫自身左右为准：左版头肩向画面右侧收，右版向画面左侧收。方向取决于身体收拢和结尾头的位置，不能靠向前伸一只爪来表达。

验收：身体明显降低并形成紧凑椭圆，前爪留在身下／头下，头枕下、闭眼；末段不重新坐起，不只向前探爪。

## 请求层还需要检查的两件事

### 同图尾帧不会因修改 prompt 自动消失

`scripts/batch_fl2va_sglang.py` 的 `load_cases()` 在未使用 `--single-frame` 且没有 `last_image` 时，会执行 `last_image = first_image`。`build_request()` 随后发出两个 keyframe 条件，`frame_index` 为 0 和 -1。

因此，I2VA 组必须使用 `--single-frame`，并检查实际请求只有第 0 帧条件。仅在 prompt 中说“无需复位”或让 `last_image` 列为空都不够。当前客户端底层 task 名仍为 `fl2va`；提示词层的 I2VA 对应它仅首帧的使用方式，不需要凭空把 task 名改成未经当前服务验证的新值。

### 4 秒、4.46 秒、输出帧时刻不是同一个概念

旧 CSV 没有 `duration_seconds` 列，客户端默认请求 4.0 秒；prompt 却把末图写在 4.46 秒。进一步读取 v2 提示词包发现，它记录了请求 4.0 秒、假定原始 107 帧、24 fps，由此计算容器时长 107/24 = 4.4583 秒，并明确标为尚待内网适配器验证。

因此，这不应直接被宣布为已确认的“4 秒请求错误”。必须核对内网实际使用的脚本版本、请求 JSON、服务端有效帧数和最终视频轨：如果输出是 107 帧且为均匀 24 fps，最后一帧 PTS 是 106/24 = 4.4167 秒，容器覆盖时长则约 4.4583 秒；二者也不能混用。

本版 CSV 显式写入设计请求时长：FL2VA 4.46 秒，打滚／睡觉 I2VA 6.0 秒，吃饭 I2VA 8.0 秒，避免客户端静默沿用 4.0 默认值。它们仍是待测请求参数，不能据此宣称服务端有效时长已验证；做 v2/v3 对照时需要把两组请求时长显式对齐。

## v3 文件与运行方式

- `data_h3/captions/v3/prompts_review_zh.md`：12 个动作的中文说明及完整英文 prompt；8 个已改写，拨球和舔爪 4 个原样保留。
- `data_h3/captions/v3/prompt_pack_v3.jsonl`：动作 ID、模式、设计时长、条件帧、修改状态、prompt 文本及哈希。
- `data_h3/metadata_smoke_v3_fl2va.csv`：3 猫 × 7 个闭环动作 = 21 条。
- `data_h3/metadata_smoke_v3_i2va.csv`：3 猫 × 5 个自然终态动作 = 15 条。

模式拆分避免把 15 条 I2VA 用默认同图首尾条件提交。CSV 中的 `prompt_mode` 是审阅字段，现有客户端不会据它自动切换条件，必须按下面两个入口分别运行。每条保留原 v2 行所用的基础 seed 数字，不能把筛选后的新行号当作原 seed。

只生成请求预览，不访问模型服务：

```bash
python3 scripts/batch_fl2va_sglang.py \
  --metadata data_h3/metadata_smoke_v3_fl2va.csv \
  --output-dir results/v3_preview/fl2va --dry-run

python3 scripts/batch_fl2va_sglang.py \
  --metadata data_h3/metadata_smoke_v3_i2va.csv --single-frame \
  --output-dir results/v3_preview/i2va --dry-run
```

内网已有兼容服务时，分别移除 `--dry-run` 并用新的输出目录运行；必要时指定 `--server-url`。不要直接套用原“两份 CSV 同时跑”的入口，它仍可能附带默认 v1 数据集。当前工作没有向内网提交推理任务。

本地验证已完成：21 条 FL2VA 和 15 条 I2VA 均通过客户端 dry-run；已核对实际请求预览中的条件帧分别为 `[0, -1]` 和 `[0]`，请求与 target 时长一致，原图片／seed 映射保留，4 个回归 prompt 文本逐字未变。记录见 `data_h3/captions/v3/validation.json`。这不代表内网视频效果已经通过。

这里的 36 条主文件保留 v2 的三只猫与全部 12 个动作，便于后续回归。不要把全部 36 条一次性跑完当作定位根因的唯一方法。

## 最小对照顺序

1. 先取实际失败例的请求与视频，核对 prompt、条件帧、seed、步数和有效视频时长。视频检查应以视频轨为准，避免把较长的音频轨当成动作时长。
2. 对一个打滚或入睡例，在同一图片、同一新版 prompt、同一 seed、同一请求时长下，只改变是否存在尾帧，检查大动作是否恢复。带尾帧组与不带尾帧组的文字要分别采用对应的官方对齐行；记录这是“条件方式”的对照。
3. 固定单首帧条件和采样设置，再分别测试原时长与 6 秒／8 秒，区分时间不足和动作语义问题。重排时间段以适配时长，并记录这项变化。
4. 对眨眼／耳朵，在相同条件和时长下比较旧文与新版；后续若需定位细因，再分别改变动作可见性和伴随反应，避免一次混改后归因于单个词。
5. 初步通过后，覆盖短毛、长毛、无毛三类猫，以及至少几个不同 seed，检查成功是否稳定。折耳／卷耳和短尾／无尾属于后续额外形态覆盖，本轮三只猫不能证明这些形态已通过。

通过标准分别按上述动作验收点记录：主动作是否出现、是否存在额外物体、是否自然、是否保留身份、方向是否正确、结尾是否符合目标。官方 skill 不替代逐视频验收。
